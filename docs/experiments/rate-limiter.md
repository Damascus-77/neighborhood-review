# 滑动窗口限流的同毫秒计数缺陷

## 问题与修复

来源脚本每次执行都用当前毫秒时间戳重置随机种子，再用“时间戳 + 随机数”生成 ZSet member。在同一毫秒内多次调用时，同样的种子生成同样的 member，ZADD 更新已有记录，ZCARD 无法反映真实请求数量，导致超过阈值仍然放行。

修复后由 Java 为每次调用生成独立 UUID，作为 Lua 的第四个参数。时间戳继续作为 score，UUID 作为 member。Lua 原子完成窗口清理、计数检查、写入与 TTL 更新。同时拒绝非正整数窗口和阈值、负数时间戳及空 member。

原脚本保存在 `src/test/resources/limiter-legacy.lua`，用于复现和回归比较，不作为生产执行脚本。

## 复现方法

执行 `scripts/test_rate_limiter.py --redis-server /path/to/redis-server`。脚本创建一个不持久化、仅监听 loopback 的独立临时 Redis，使用固定的请求时间戳构造同毫秒场景。并发场景使用 20 个客户端线程和独立 TCP 连接。

Java 的 `RateLimiterAspectTest` 验证同一切面连续调用时，实际发送给脚本的第四个参数为两个不同的 UUID。

原始观测记录见 [rate-limiter-results.json](rate-limiter-results.json)。结果应在脚本和 Java 测试通过后解读。

## 2026 年 10 月 27 日实测

| 场景 | 条件 | 观测结果 |
| --- | --- | --- |
| 旧脚本复现 | 同毫秒 200 个请求，60 秒窗口阈值 10 | 放行 200，ZSet 只有 1 条记录 |
| 修复脚本 | 相同时间戳、窗口和请求数量 | 放行 10，ZSet 为 10 条记录 |
| 并发回归 | 20 个线程提交 200 个请求，阈值 25 | 放行 25，ZSet 为 25 条记录 |
| 窗口边界 | 1 秒窗口、阈值 1；时间偏移 0/999/1000ms | 返回 1/0/1，左边界按约定移出窗口 |
| 其他回归 | Key 隔离、TTL、非法参数 | 全部通过 |

真实 Redis 回归共 7 项检查通过；JDK 21 下的 Maven 测试执行 1 项 Java 参数回归，0 失败、0 错误。测试过程没有启动完整业务应用。

## 指标边界

这是计数正确性与边界回归，不是 JMeter HTTP 压测，也没有测量全系统 QPS、接口延迟或生产容量。旧脚本与修复脚本使用相同的请求时间戳和阈值进行比较。

脚本回归使用本地可用的 Redis 3.2.100 Windows 二进制，仅验证所涉及的 Lua、ZSet 和 TTL 命令。完整应用涉及 GEOSEARCH 等其他命令，其 Redis 版本要求仍按 README 的 6.2+ 准备；当前实验不能代表对所有部署版本的兼容性验证。

UUID 大幅降低不同请求 member 冲突的概率；该方案仍依赖各调用方使用同一套接口约定，并未解决多实例时钟偏差。用户身份、代理 IP 信任策略、Redis 不可用时的处理和 HTTP 级限流响应仍属于后续工作。
